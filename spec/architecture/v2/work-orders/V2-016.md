# V2-016 — Cross-Device Attestation Runtime Preconditions

**Status:** frozen work order  
**Generation:** WorkflowOS 2.0  
**Architecture change:** V2-ACR-001 — Verifiable Execution and Execution Attestation  
**Wave:** W5 corrective prerequisite for IG-006  
**Depends on:** `implementation: V2-008` (existing computer-agent runtime), `contract: V2-014` (ExecutionAttestation / VerifiedExecutionFact), `integration: IG-006` (must be re-run after this work; current IG-006 remains blocked)

## Architectural finding being corrected

IG-006 repository review established two missing composition couplings in the already-merged V2-008 surface:

1. a dependent action can currently resume without consuming any admission/precondition derived from an independently verified predecessor attestation;
2. V2-008's production attestation material has no way to carry the causal predecessor execution digest, so the runtime-produced dependent attestation is unparented.

IG-006 must remain fail-closed until both couplings are available. This Work Order supplies the minimum runtime contract required for IG-006 to prove the frozen cross-device protocol without modifying V2-005/V2-009/V2-014 inside the gate.

## Objective

Extend the V2-008 computer-agent runtime with **explicit, non-authoritative composition hooks** that allow a future/adjacent proof-graph or coordination authority to provide a verified predecessor precondition and causal-parent commitments, while V2-008 remains solely responsible for executing the workflow step and enforcing that the supplied precondition is consumed before the dependent side effect and that the runtime-produced attestation faithfully records the declared causal parents.

The work must make IG-006 able to demonstrate the real runtime path, not a test-only protocol probe.

## Ownership boundary

V2-008 owns:

- the execution boundary at which a dependent computer step is admitted into the runtime action loop;
- the typed runtime input needed to carry a caller-supplied verified predecessor precondition;
- fail-closed enforcement that the required precondition is present and valid for the declared predecessor/dependent relationship;
- propagation of declared causal-parent execution digests into the runtime-produced `ExecutionStatement` / `StepAttestationMaterial`;
- typed runtime rejection and zero-side-effect behavior when the precondition or causal binding is absent/invalid.

V2-008 does **not** own:

- proof-graph storage or graph topology (V2-015);
- verification authority or cryptographic primitives (V2-014);
- authorization authority (existing safe-action policy remains authoritative);
- WorkflowIR dependency semantics (V2-003);
- Run/evidence persistence authority (V2-005);
- node identity/capability/placement authority (V2-004/V2-009);
- marketplace/collaboration semantics.

No second verification, authorization, workflow, or proof-graph engine may be introduced.

## Required contract

### 1. Explicit dependent-action precondition

The public V2-008 execution/resume surface must accept a typed composition precondition for a dependent step. The exact TypeScript names may follow repository conventions, but the contract must expose at least:

- the dependent step identity;
- the predecessor attestation/execution identity being relied upon;
- the verified execution fact produced by the canonical V2-014 verifier, or an equivalently typed V2-014-derived fact that is impossible to confuse with raw/unverified attestation bytes;
- the relationship/parent execution digest(s) that the dependent step is declaring;
- enough stable Run/WorkflowVersion identity to prevent cross-run/cross-version substitution.

The runtime must consume this precondition **before the first dependent side-effecting host invocation**. Presence in an argument object is insufficient: the test must prove a missing, stale, wrong-run, wrong-version, wrong-step, unverified, or otherwise invalid precondition prevents the dependent side effect.

V2-008 must not silently reinterpret a verified fact as authorization. Capability grants and human authorization remain separate dimensions.

### 2. Canonical verification boundary

V2-008 must consume verification results from the existing V2-014 public contract. Do not duplicate signature parsing, signing, freshness, replay, or attester-policy logic inside V2-008.

The runtime may enforce structural binding of a V2-014-derived verified fact to the current Run/WorkflowVersion/step/predecessor relationship, but it must not create an alternative cryptographic verification authority.

### 3. Causal-parent production

Extend the V2-008 attestation-production material so a dependent execution can declare one or more causal predecessor execution digests. Those values must flow unchanged into the canonical V2-014 `ExecutionStatement.causalParents` field produced by the runtime.

Requirements:

- the production path must never invent a parent digest;
- parent ordering must be deterministic;
- the runtime-produced dependent attestation must carry exactly the declared parents;
- an execution declared as dependent cannot silently fall back to `causalParents: []` when a causal precondition is required;
- the stored attestation must remain otherwise identical in semantic ownership and use the existing V2-014 production/signing path.

### 4. Fail-closed admission

For a step configured to require a verified predecessor:

- no verified predecessor → typed rejection, zero host side effects;
- wrong predecessor/run/version/step binding → typed rejection, zero host side effects;
- stale/replayed/insufficient-assurance predecessor surfaced by the canonical V2-014 verifier → typed rejection, zero host side effects;
- valid predecessor precondition → dependent execution may proceed subject to the existing capability, authorization, placement, and runtime safety gates.

The runtime must not treat a raw `ExecutionAttestation`, signature validity, or attester identity alone as sufficient admission.

## Required regressions

At minimum, add deterministic integration/regression coverage for:

1. valid predecessor precondition is consumed before the first dependent side effect;
2. missing precondition fails closed before any side effect;
3. wrong run binding fails closed;
4. wrong WorkflowVersion binding fails closed;
5. wrong predecessor/step binding fails closed;
6. unverified/stale/replayed predecessor fails closed through V2-014-derived verification results;
7. insufficient attestation assurance fails closed;
8. capability advertisement remains distinct from authorization;
9. a dependent runtime-produced attestation contains exactly the declared causal parent digest(s);
10. zero-parent behavior remains valid for non-dependent steps;
11. duplicate/re-drive of the admitted dependent action remains exactly-once under the existing V2-005/V2-008 idempotency mechanisms;
12. the precondition cannot be supplied for one Run/WorkflowVersion and consumed by another.

Tests must exercise the actual public V2-008 execution/resume path. A hand-built `ExecutionStatement` is insufficient proof of runtime causal production.

## Required dogfooding contribution

Provide the minimum dogfooding needed for IG-006 to re-prove:

- Node A produces an attestation;
- the canonical V2-014 verifier independently verifies it;
- the resulting V2-014-derived verified fact is passed into Node B's dependent execution boundary;
- Node B consumes that precondition before its first side effect;
- the dependent Node-B attestation records Node A's execution digest in `causalParents`;
- negative precondition cases produce typed rejection with zero side effects;
- replay/duplicate delivery still converges.

V2-016's own dogfooding should remain narrowly focused on the newly added runtime contract. Full cross-device completion is re-proven by IG-006 after this work merges.

## Static architecture constraints

Add architecture/static checks that:

- keep all new composition types behind the V2-008 public barrel;
- forbid consumers from reaching into V2-008 internals;
- forbid a second verification/signing implementation;
- forbid V2-008 from importing V2-015 implementation code;
- preserve the existing V2-005 recorder boundary;
- preserve the existing authorization and capability boundaries;
- require the causal-parent field to reach V2-014's canonical statement rather than being stored only in test metadata.

## Non-goals

Do not:

- implement `ExecutionProofGraph` (V2-015);
- change V2-014 attestation cryptographic semantics;
- redesign Run persistence or add a new database authority;
- add payment, marketplace, blockchain, ZK, hardware-attestation, or transparency infrastructure;
- change WorkflowIR semantics to encode proof-graph edges;
- bypass existing authorization, placement, freshness, replay, or evidence rules;
- add platform-specific causal semantics for web/desktop/mobile.

## Completion gate

V2-016 is complete only after:

1. the implementation changes only V2-008-owned source/contracts plus its deterministic tests/evidence;
2. all required regressions are green;
3. the existing architecture suite remains green;
4. typecheck/lint show no new baseline errors;
5. targeted dogfooding proves the real runtime path consumes the verified predecessor precondition and emits the declared causal parents;
6. a fresh re-run of IG-006 proves P3 on the runtime admission path and P5 on the runtime attestation-production path;
7. sole architect review/merge and actual merge evidence are recorded.

V2-015 remains blocked until IG-006 is genuinely complete. No implementation may activate V2-015 merely because V2-016 itself merges.

## Stop conditions

Stop and raise a governed architecture change if satisfying this Work Order would require:

- introducing a second verification/signing authority;
- making signatures imply trust or authorization automatically;
- moving WorkflowIR semantics into the proof graph;
- weakening replay/freshness/assurance checks;
- centralizing node trust;
- modifying V2-014 semantics rather than consuming its public contract;
- creating a second execution or authorization engine.
