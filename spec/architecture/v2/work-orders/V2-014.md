# V2-014 — Execution Attestation Protocol

**Status:** in-flight  
**Generation:** WorkflowOS 2.0  
**Architecture change:** V2-ACR-001 — Verifiable Execution and Execution Attestation  
**Wave:** W2A (parallel with V2-006 and V2-007)

## Objective

Implement the protocol-native execution commitment and attestation primitives that make a bounded WorkflowOS execution fact deterministic, authenticated, freshness-bound and independently appraisable without changing WorkflowIR or creating a second execution/verification authority.

## Dependencies

- `contract: V2-003` — canonical WorkflowIR/semantic-digest contract;
- `contract: V2-004` — Node identity/capability/trust/placement contract;
- `contract: V2-001` — universal protocol and message/conformance contract;
- `architecture: V2-ACR-001` — approved repository evolution governing the attestation semantics.

This Work Order does NOT depend on an unmerged sibling implementation. It may start only after W1 contracts are merged/frozen and V2-ACR-001 is accepted into the repository's governing state.

## Owns

- ExecutionStatement schema and canonical serialization;
- domain-separated ExecutionDigest;
- ExecutionAttestation envelope/signature model;
- attester/workload identity bindings;
- freshness and anti-replay semantics;
- assurance vocabulary and capability to represent assurance evidence;
- cryptographic verification primitives and typed failure results;
- protocol conformance fixtures and discrimination tests for these contracts.

## Does not own

- WorkflowRepository or WorkflowVersion persistence (V2-002);
- WorkflowIR semantics (V2-003);
- Node implementation/identity authority (V2-004);
- WorkflowRun persistence/state/evidence authority (V2-005);
- computer-use execution (V2-008);
- cross-device proof-graph coordination (V2-015);
- a new workflow, authorization, or verification engine;
- blockchain/transparency infrastructure;
- mandatory hardware/TEE support on hosts that cannot provide it.

## Required invariants

1. ExecutionDigest is distinct from WorkflowVersion semantic digest.
2. Canonical serialization is deterministic and domain-separated.
3. Every decision-relevant attestation binds to the exact WorkflowVersion, Run, execution attempt, and applicable step.
4. Attestation identity is distinct from Node identity and workload identity.
5. Signature validity never implies authorization, correct behavior, or sufficient evidence.
6. Freshness is mandatory where an attestation can influence current execution; timestamps alone are insufficient replay protection.
7. Cross-protocol and cross-object substitution is rejected by typed/domain-separated verification.
8. Sensitive data and secrets are not leaked into the attestation payload.
9. Assurance levels are explicit properties and cannot change WorkflowIR semantics.
10. Unsupported stronger assurance is reported honestly and never silently downgraded.
11. The primitive introduces no second workflow, execution, authorization, or verification authority.
12. Existing evidence classes remain distinct; attestation is an authenticated protocol object, not a replacement evidence class.

## Required verification

- deterministic canonicalization and digest equality across implementations;
- domain-separation discrimination tests;
- signature generation/verification and malformed-envelope rejection;
- wrong WorkflowVersion / Run / attempt / step binding rejection;
- replay with valid signature but stale nonce/epoch rejection;
- duplicate attestation convergence by stable identity;
- cross-attester/key substitution rejection;
- capability-vs-authorization discrimination;
- assurance downgrade rejection where policy requires stronger assurance;
- secret/payload non-leakage tests;
- mutation/discrimination tests proving removal of each critical check causes the corresponding test to fail;
- real cryptographic primitives, not mocks, for the verification path.

## Required dogfooding

Use a real execution-capable host and a real WorkflowRun to produce an attestation for a safe, deterministic action. Export the attestation and independently verify it outside the issuing code path. Then perform a negative experiment using a replayed/stale or modified attestation and record the rejection. The experiment must record exact WorkflowVersion/Run/Node, expected statement, observed attestation, verification result, and any findings.

No production destructive actions are required; use an isolated test resource where a side effect is needed.

## Parallelism contract

V2-014 is designed to run in parallel with V2-006 and V2-007 after W1 because it owns only the attestation contract/cryptographic surface. It does not modify sibling internals. V2-005 is intentionally delayed until V2-014's contract is merged because V2-005 owns durable Run/evidence records that must reference the attestation contract without inventing a competing schema.

The branch MUST start from the same stable `main` SHA as other W2A siblings. It MUST NOT consume, branch from, or rebase onto an unmerged sibling.

## Completion gate

V2-014 is COMPLETE only after implementation, deterministic verification, required real-crypto proof, feature-boundary dogfooding, sole architect review/merge, actual merge evidence, and post-merge state finalization.

## Stop conditions

Stop and raise a governed V2 architecture change if implementation would require:

- treating a signature/hash as automatic evidence of a physical side effect;
- mandatory hardware/TEE or ZK support for every host;
- a new workflow/authorization/verification authority;
- changing WorkflowIR semantics;
- putting secrets in attestation payloads;
- weakening freshness/replay protection;
- platform-specific attestation semantics that fork the universal protocol;
- making an external ledger/blockchain mandatory for correctness.
