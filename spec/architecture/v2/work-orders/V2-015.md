# V2-015 — Execution Proof Graph and Trust-Minimized Coordination

**Status:** planned  
**Generation:** WorkflowOS 2.0  
**Architecture change:** V2-ACR-001 — Verifiable Execution and Execution Attestation  
**Wave:** W5 (parallel with V2-012)

## Objective

Compose independently produced ExecutionAttestations into a verifiable causal/dependency graph so workflows can coordinate across heterogeneous and independently administered nodes using explicit trust, authorization, freshness and assurance policies.

## Dependencies

- `implementation: V2-014` — execution attestation primitives;
- `implementation: V2-005` — durable WorkflowRun/evidence records;
- `implementation: V2-008` — computer-agent runtime and cross-host execution;
- `implementation: V2-009` — events, schedules, placement and locality;
- `integration: IG-006` — cross-device attestation composition.

V2-015 must consume only merged implementations and completed integration gates. It never consumes an unmerged sibling branch.

## Owns

- ExecutionProofGraph model and serialization;
- causal and dependency edge semantics between attestations;
- admission predicates based on VerifiedExecutionFacts;
- cross-device continuation that preserves Run/WorkflowVersion identity;
- multi-parent dependency satisfaction;
- replay/duplicate convergence at graph level;
- trust-policy evaluation inputs specific to proof composition;
- dedicated graph and coordination tests.

## Does not own

- WorkflowIR semantics or a second workflow graph (V2-003 remains authoritative);
- Run lifecycle/evidence storage (V2-005);
- Node identity/capability authority (V2-004);
- computer-use execution (V2-008);
- generic event/scheduling authority (V2-009);
- authorization authority;
- verification authority;
- marketplace entitlement or blockchain infrastructure.

## Required invariants

1. The proof graph is evidence about executions, not a replacement for WorkflowIR.
2. Every graph node is bound to a valid ExecutionAttestation and stable execution identity.
3. Causal edges are acyclic and deterministically ordered.
4. A dependent action cannot be admitted from an unverified, stale, unauthorized, or insufficient-assurance predecessor.
5. Cross-device handoff preserves WorkflowVersion, Run and causation identity and does not duplicate side effects.
6. Independent branches may execute in parallel only when the declared workflow dependencies and placement/policy rules permit them.
7. Repeated delivery or replay converges to one logical graph fact.
8. Trust policy remains explicit; signature validity never silently becomes trust.
9. Node capability, authorization, placement, attestation assurance and verification result remain separate dimensions.
10. A malicious coordinator cannot alter the graph without detection because node identity, parent commitments and canonical graph relationships are verified.
11. The graph cannot erase or rewrite prior verified execution facts.
12. No second workflow, execution, verification, or authorization engine is introduced.

## Required verification

- single-node and multi-node proof-graph construction;
- causal-parent mismatch rejection;
- missing-parent and cyclic-graph rejection;
- replayed attestation rejection;
- stale/freshness-bound attestation rejection;
- multi-parent dependency admission and denial;
- conflicting branch convergence;
- duplicate delivery/idempotency;
- cross-device handoff recovery after disconnect/reconnect;
- malicious graph coordinator mutation detection;
- assurance-policy enforcement and explicit insufficient-assurance results;
- capability-vs-authorization discrimination;
- mutation/discrimination tests for every critical graph-integrity and admission check;
- real cryptographic verification with independent verifier context.

## Required dogfooding

Run one real workflow across at least two supported hosts where locality/capabilities permit. Produce attestations on the first host, transfer the run to another host, require a verified predecessor predicate before the next side effect, and record the complete proof graph. Then repeat/replay one attestation or deliver one graph fragment twice and demonstrate deterministic rejection/convergence.

The cross-feature experiment must use safe/isolated effects and preserve negative findings as append-only evidence.

## Parallelism contract

V2-015 runs in parallel with V2-012 after its dependencies and IG-006 are complete. The two own disjoint authoritative surfaces: proof-graph/coordination versus collaboration/marketplace/economics. No branch may rebase onto the sibling.

## Completion gate

V2-015 is COMPLETE only after deterministic tests, real cryptographic verification, cross-device integration proofs, feature-boundary dogfooding, sole architect review/merge, actual merge evidence and post-merge finalization.

## Stop conditions

Stop and raise a governed architecture change if implementation requires:

- a second workflow protocol or graph whose semantics compete with WorkflowIR;
- automatic trust from signatures without appraisal policy;
- centralization of all nodes into one mandatory trust authority;
- weakening of freshness/replay protection;
- silent cross-device duplication of a side effect;
- mandatory blockchain/transparency infrastructure for baseline correctness;
- mandatory hardware attestation or ZK proofs on all hosts;
- a platform-specific workflow semantic fork.
