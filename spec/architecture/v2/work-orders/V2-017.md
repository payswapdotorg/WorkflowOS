# V2-017 — Universal Product UX

**Status:** planned / governance activation pending
**Dependency:** `architecture: V2-ACR-003`
**Wave:** post-W6 product layer

## Objective
Transform WorkflowOS's human-facing frontend into the approved universal product UX without redefining any V2 semantic or authority contract.

## Product model

Primary verbs: **MAKE / DO / LEARN / SHARE / IMPROVE**.

Primary navigation: **Home / Workflows / Explore / Activity**.

Universal entry: **Search / Ask / Create**.

Primary workflow actions: **Run / Teach Me / Edit**, with scheduling contextual.

Progressive disclosure: **DO → UNDERSTAND → CONTROL → INSPECT**.

## Owns
- human-facing information architecture;
- navigation and responsive shell;
- workflow library and workflow detail presentation;
- natural-language / voice / demonstration entry surfaces over existing authoring authorities;
- run, approval, pause/resume/takeover and recovery presentation;
- where-it-runs, scheduling and event presentation;
- teaching and reverse-teaching presentation;
- access/safety presentation;
- activity/history and trust/evidence disclosure;
- version/update and optimization presentation;
- sharing, marketplace and installation presentation;
- expert-mode entry to the existing engineering control surface.

## Does not own
- WorkflowIR semantics;
- Workflow / WorkflowVersion authority;
- Run lifecycle/evidence authority;
- Node/Capability authority;
- authorization or placement authority;
- teaching semantics;
- marketplace economics;
- execution attestation/proof semantics;
- development governance;
- any second workflow protocol or execution engine.

## Non-negotiable UX/architecture rules

1. Conversation is an input mechanism, never a durable workflow format.
2. User-facing terminology may simplify internal concepts but cannot alter their semantics.
3. Failed reads must remain visibly unavailable, never become successful empty states.
4. A workflow version shown as installed remains pinned until an explicit adoption action succeeds.
5. A purchase/entitlement may never be presented as execution authorization.
6. Cryptographic signatures, digests and attestations may support a trust explanation but must not be presented as automatic proof of a physical side effect.
7. Unsupported device capabilities must be honestly disclosed.
8. The existing developer/engineering workspace remains reachable; it is re-contextualized, not deleted.
9. Any required backend addition must consume an existing public authority. A missing authority contract is a stop-and-escalate condition, not a UI-side invention.

## Acceptance criteria

- Primary navigation matches the approved human-facing model.
- Internal architecture terms are removed from primary UX and appear only in expert/inspection contexts.
- Workflow detail communicates purpose, Run/Teach Me/Edit actions, state, steps, when/where it runs, recent activity, version and access/safety.
- Tell / Show / Tell + Show creation entry points exist without creating a second workflow representation.
- Run, pause, resume, takeover and failure UX preserve the existing Run authority.
- Scheduling/event UX uses human-readable language while preserving canonical trigger/event semantics.
- Teach Me and reverse teaching are first-class and visibly distinct from execution evidence.
- Access UX uses “Needs access to” while preserving capability/authorization/consent separation.
- Update UX makes immutable version pinning visible.
- Optimization UX presents proposals as new versions and requires adoption.
- Marketplace/share UX preserves entitlement vs installation vs execution boundaries.
- “How do you know?” exposes concise evidence first and advanced verification on demand.
- Expert workspace remains accessible.
- Desktop/tablet/mobile layouts are platform-appropriate rather than a shrunken desktop.
- Automated frontend tests cover navigation, disclosure, authorization language, unavailable-vs-empty state, pinning, and recovery affordances.
- Real browser dogfooding proves at least one representative end-to-end journey.

## Required verification

- frontend typecheck;
- frontend lint;
- frontend component/unit tests;
- relevant browser E2E suites;
- exact-head CI verification;
- real browser dogfooding;
- architecture/static checks confirming no frozen-contract or authority drift.

## Scope exclusions

No change to V2 protocol names, WorkflowIR, run state machines, execution-proof semantics, marketplace economics, governance semantics, or existing backend authority ownership merely to make the UX simpler.
